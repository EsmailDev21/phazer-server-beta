# ADR-0014 - GitHub: webhook, repo links, key parser, status rules

Status: ACCEPTED (step 2.6). Owner forks answered: repo is linked from the installation's repository list through admin REST (as in 2.3); a PR/branch link cannot be removed by the user.

## Context
The GitHub App (connect, installation tokens) existed since 2.1. 2.6 makes it do something: a PR, branch, commit or issue that names a task key attaches itself to that task, and PR events can move the task. The risk is tenancy: GitHub text is written by strangers, so a key must never reach a task outside the workspace the admin linked.

## Decisions
1. **Tenant chain.** installation id -> the ONE live GITHUB connection (account) -> `(connection, REPO, repo id)` `ChannelLink` (workspace, project) -> task. Unknown installation, unlinked repo, paused link, non-ACTIVE connection: ignored before anything from the payload is used. The linked workspace must belong to the connection's account (checked again).
2. **Webhook.** `POST /integrations/github/webhook`, `@PublicSigned`. `X-Hub-Signature-256` = HMAC-SHA256 of the RAW body with `GITHUB_WEBHOOK_SECRET` (min 16 chars; absent = every request 401), constant-time, checked FIRST. GitHub has no timestamp, so replay protection is the delivery id (`X-GitHub-Delivery`, 7-day dedupe, claim released if the enqueue fails). `ping`, unsupported events and actions are answered 200 and dropped BEFORE dedupe. The payload is reduced to a small validated `GithubWork` (caps on title, body, commits; repo name pattern; numeric ids) and ONLY that goes to the queue `webhooks` / job `github.event`. Verified against GitHub's published signature example.
3. **Events.** `pull_request` (opened, reopened, ready_for_review, converted_to_draft, closed, edited), `issues` (opened, reopened, closed, edited; real issues only), `push` (branch pushes; a link per commit that names a key, plus the branch), `create` (branch), `installation` (deleted, suspend, unsuspend), `installation_repositories`.
4. **Key parser.** Candidates `[A-Za-z][A-Za-z0-9]{1,9}-\d{1,9}` not glued to other letters/digits, case-insensitive, max 20 per item, from: PR title + head branch + body; issue title + body; each commit message; the branch name. The regex is deliberately generous (`UTF-8` is a candidate): the GATE is resolution. A candidate becomes a task only if its key is a current key or retired alias of the LINKED workspace (`WorkspaceKeysService.resolve` within the account, then `workspaceId ===`) and that number exists there. OPS-1 from another workspace of the same account, or another account's ENG-1, never links. At most 10 tasks per item.
5. **Links.** `ExternalLink` (provider GITHUB; kinds PR, ISSUE, COMMIT, BRANCH), upserted by the 1.6 key; `externalId` uses the numeric repo id (`{repoId}#{n}`, `{repoId}@{sha}`, `{repoId}:{branch}`) so a repo rename does not duplicate. The URL is BUILT from the validated `owner/name`, never copied from the payload. State is the provider's word with two guards against out-of-order deliveries: `merged` is final; `closed` only reopens through a `reopened` action. First creation writes one `EXTERNAL_LINKED` activity (new enum value): TIMELINE for PR and ISSUE (channels hear "Linked PR #12"), SILENT for COMMIT and BRANCH (history only, no flood). Re-delivery changes no row count and writes no second activity. No in-app notification.
6. **Status rules** in `ChannelLink.config` (new `config JSONB`): `{repoFullName, statusRules: {prOpened, prMerged, prClosed}}`, values are workflow CATEGORIES (`TaskStatus`), the project's workflow picks the concrete status. Defaults, stored explicitly at link time: opened -> IN_PROGRESS, merged -> DONE, closed unmerged -> none. Rules fire on opened / reopened / ready_for_review (opened), closed+merged (merged), closed (closed). `edited`, `converted_to_draft`, pushes and issues never move a task. Safety: opened and merged only move FORWARD (rank TODO 0, IN_PROGRESS = BLOCKED 1, DONE 2), so a new PR never unblocks a Blocked task and a reopened one never drags a Done task back; a configured closed rule may move backwards but NEVER out of DONE (another PR may have finished it). The change goes through `TasksService.update` (workflow resolution, STATUS_CHANGED activity and normal channel messages); a refusal (e.g. enforced transitions) is logged and skipped, never fails the delivery. Phase 5 turns these into Automations.
7. **Actor.** Attribution only: the GitHub sender is looked up in `IdentityLink` by numeric GitHub user id (as a string); mapped = that user is the activity actor, otherwise `null` (the "GitHub" system actor; metadata carries the login). The rules are the admin's configuration, so no per-user permission check. `TasksService.update` now accepts a null actor and an optional write context + extra activity metadata (`source: {provider, kind, ref, repo}`).
8. **Installation lifecycle.** `deleted`: connection REVOKED, credential deleted, REPO links KEPT but paused, one `INTEGRATION_DISCONNECTED` audit row with `system: true` (owners/admins get the ACCOUNT_ALERT); replays are no-ops. `suspend`/`unsuspend`: ACTIVE <-> ERROR('GitHub App suspended') only (unsuspend never revives an ERROR that has another cause). `installation_repositories`: removed repos pause their links, added ones resume them only while the connection is ACTIVE.
9. **Admin API** (`manageIntegrations`, same authority as 2.3, resolved from the connection): `GET /integrations/connections/:id/github/repositories?page` (what the installation sees, with `linkId` when already linked), `POST .../github/repo-links {repoId, projectId, statusRules?}` (workspace comes from the project; project of another account = the same error as a missing one; the repo is re-checked against GitHub with the installation token; duplicate = 409), `PATCH /integrations/channel-links/:linkId/github-rules {statusRules}` (only the keys sent change, null clears). Listing and deleting links reuse the 2.3 routes (listing now includes `config`). A CHANNEL link can no longer be created on a GitHub connection. The user cannot remove an individual PR/branch link (owner decision: the next webhook would re-add it; fix the PR title instead).
10. **Modules.** `IntegrationGithubModule` in API and worker.

## Found by the tests
- An empty body passed validation on the rules route (`@ValidateNested` ignores a missing value): `@IsDefined()` added.
- Six mutations were run against the safety lines (key resolved in any workspace, account-consistency check, forward-only, DONE protection, signature check, ACTIVE-connection filter); each was caught.

## Not done
Removing a link; per-event rules beyond PR opened/merged/closed; review / CI-check events; GitHub Enterprise Server (URLs are github.com); linking a repo from the GitHub side; a debounce for very busy pushes (commit links are capped at 20 per push by GitHub itself); the web UI. Nothing ran against real GitHub: payload shapes follow the documentation and are tested with signed fixtures; the two new REST calls (`/installation/repositories`, `/repositories/{id}`) are tested with mocked HTTP.
