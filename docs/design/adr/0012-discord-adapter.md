# ADR-0012 - Discord adapter: interactions, chat commands, notify

Status: ACCEPTED (step 2.4). No owner fork was raised: the spec fixes the permission model and the app is product-owned (as 2.1 already assumed).

## Context
Discord sends every slash command, context-menu click, button and modal submit as an HTTPS POST to ONE endpoint and requires an answer within 3 seconds.
2.1-2.3 gave connections, identity and the notification router; 2.4 makes Discord useful in both directions.

## Decisions
1. **One product-owned Discord application** for all customers (env `DISCORD_CLIENT_ID/SECRET/PUBLIC_KEY/BOT_TOKEN`), each customer's server is a connection (ADR-0009). Bring-your-own-bot is not supported.
2. **Neutral core.** Discord payloads are parsed into a provider-neutral `ChatIntent` (create, create_from_message, update, assign, assign_me, set_due, list, link); ONE `ChatCommandExecutor` runs it. Slack (2.5) will add a parser and reuse the executor.
3. **Interactions endpoint** `POST /integrations/discord/interactions` (`@PublicSigned`, flag INTEGRATIONS). The Ed25519 signature over `timestamp + RAW body` is verified **first**: nothing is read, written or enqueued for an unverified caller. Timestamps more than 5 minutes off are `expired` even when correctly signed (replay). Any failure, including an unset/malformed `DISCORD_PUBLIC_KEY` (fail closed), is the same bare 401. Then: PING -> PONG; duplicate interaction ids are claimed once (`WebhookDedupeService`).
4. **Authority = the linked user's, never the bot's.** The guild id (from the signed payload) maps to the ONE live connection; the caller's Discord id maps through `IdentityService.resolve` (ADR-0010). Unlinked -> an ephemeral link prompt (the one-time token only ever appears in that reply). The executor then asks the `PermissionResolver` for the real action (`createTask` on the workspace incl. plan limit, `editTask`/`assignTask` on the task, `linkChannel` on the workspace) and the visibility service for existing tasks. Task keys and button task ids are resolved **inside the connection's own account**: someone who belongs to two accounts cannot reach the other account's tasks through this server's bot (tested with a dual-account user; a task you cannot see answers exactly like one that does not exist). Assigning someone else uses `lookupLinkedUserId`, which is read-only: it never issues a link token (a token handed to the caller would let them claim the other person's identity).
5. **The 3-second rule.** Synchronous: verify, parse (pure), dedupe, connection + identity (indexed reads), preflight, one enqueue. Heavy work is the `chat.command` job (queue `chat`, flag INTEGRATIONS, enqueued with a 250 ms head start so the follow-up cannot overtake Discord processing our deferral; a 404 retries anyway). `create` is acked PUBLIC (the channel sees the confirmation, so the echo guard of ADR-0011 skips that channel); update/assign/due/list/link are acked EPHEMERAL (the channel, if subscribed, hears the change through the router instead of a duplicate). `executor.preflight` runs the refusable checks of a public command BEFORE the ack so a refusal is private, not shown to the room. Queue unavailable -> a private "busy" reply, never a hung "thinking...".
6. **Message -> task.** The message context-menu command opens a modal (title = first line, description = the message, optional project); the submit creates the task AND an `ExternalLink` in one transaction: `MESSAGE` (url to the message) or `THREAD` for a forum post/thread starter (starter message id == thread channel id, channel types 10/11/12 - from Discord's docs, not exercised live). A message that already has a task in that workspace is refused ("already created").
7. **Writes at-most-once, replies at-least-once.** `chat_command_runs(provider, interaction_id)` is inserted (RUNNING) before the executor runs and set DONE with the result after. A retried job re-posts the stored result; a leftover RUNNING row means the attempt died mid-write, so it does NOT run again (it could double-create) and tells the user the outcome is unknown. An unexpected failure becomes a generic private message with no internals and is recorded DONE (not retried).
8. **Commands are registered per guild** after a successful connect (`adapter.afterConnect`, best effort, needs `DISCORD_BOT_TOKEN`; guild commands appear instantly, global ones take up to an hour). A failure never fails the connect.
9. **One live connection per provider tenant**, enforced by a partial unique index on `(provider, external_account_id)` for ACTIVE/NEEDS_REAUTH/ERROR (an interaction carries only a guild id, so it must map to exactly one account). The callback answers `?error=already_connected`; REVOKED rows do not block; to move a server, disconnect first.
10. **`/task link`** needs Discord Manage Server (or Administrator) **and** workspace-admin rights in the app (`linkChannel`). `workspace:KEY` links the server (GUILD link), `project:NAME` links THIS channel (CHANNEL link) and creates the default subscription once. No options shows the current link.
11. **Notify** posts one embed per `RichMessage` with the bot token and `allowed_mentions: none`; 400/401/403/404 are `NotifyPermanentError` (retrying cannot help), 5xx/network are transient; `X-RateLimit-Remaining: 0` delays the next post to that channel until the reset (in-process window; waits over 5 s become a transient error so the queue retries); 429 is the shared HTTP client's.

## Consequences / not done
- No autocomplete (project/workspace are typed names), no `unlink`/comment/delete commands, `status` takes the 5 categories (not a project's custom workflow statuses).
- A task created from chat records origin INTEGRATION and the echo source; `update`/`assign` do not (their reply is private), so a subscribed originating channel hears them through the router.
- If the executor fails unexpectedly AFTER a public ack, the room sees a short generic error text.
- Slash command names/choices are fixed in `DISCORD_COMMANDS`; changing them needs re-registration (reconnect the server or call `afterConnect`).
- Nothing was exercised against real Discord: signature scheme, payload shapes, the follow-up PATCH and command registration follow the documentation and are tested with signed fixtures and mocked HTTP.
