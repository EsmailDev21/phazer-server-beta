# ADR-0033 - Import executor, chunked writes and rollback

Status: ACCEPTED (step 4.4). Follows ADR-0030 (core), 0031 (CanonicalBundle), 0032 (mapping), and ADR-0003 (DomainWriter).

## Decisions
1. **One loop, in the worker.** `imports.run` -> `ImportExecutor`: fetch a page (`adapter.fetchBundle(cursor)`) -> `validateBundle` -> `applyMapping` -> write (structure, tasks, dependencies) -> checkpoint -> repeat; then the LINKS phase; then finish. A queue job handles at most 40 pages and hands the import back (`RUNNING -> QUEUED`, next attempt) so jobs stay short.
2. **The row is the only truth.** A queue job acts only if `payload.attempt === job.attempt` and the status is QUEUED / RUNNING (re-delivery after a worker death) / PAUSED (its own delayed retry). Every state change is a compare-and-set on `status = RUNNING`; a cancel is seen at the next page boundary and nothing can resurrect a canceled or finished job.
3. **Crash safety by construction.** The checkpoint (cursor) advances only after a page is fully written. Each chunk's rows, `ExternalRef`s, tags, custom values, pending links, usage charge and progress counters commit in ONE transaction (`DomainWriter.createTasksBulk` gained `afterChunk`, the companion of `filterChunk`). A crash re-fetches the same page; the ref lookups make that a no-op (guard 1: page-level lookup; guard 2: re-checked inside the chunk transaction, for a concurrent run). Tests kill a run between pages and in the middle of a page.
4. **Errors are classified** (`classifyImportError`, a table): AUTH and PLAN_LIMIT -> PAUSED (the person resumes); RATE_LIMIT and TRANSIENT -> PAUSED + a delayed `imports.run` of the next attempt (15 s doubling to 10 min; a rate limit waits what the provider asked, bounded), at most 8 in a row, then FAILED (resumable); an ITEM error (our own writers refusing this data) is isolated and the import goes on; everything else -> FAILED with a plain-language reason (never a stack, never a provider body). Resuming bumps `attempt`, so a stale delayed retry cannot run.
5. **Poison items are isolated by bisection, then by dropping associations.** A refused chunk is split until one task remains; that task is retried without each optional association in turn (parent, iteration, issue type, workflow status), then without all of them, and kept with a WARN naming what was left out (`PARENT_REJECTED`, `ITERATION_REJECTED`, ...). Only if nothing helps is it `TASK_REJECTED` (ERROR). The task matters more than its sprint.
6. **Tasks are written level by level** (in-page depth), so a child's parent is already committed and referenced when its level starts; no index remapping, bisection stays trivial. A parent or dependency whose other end is on a LATER page goes to `import_pending_links` (a table, in the same transaction), resolved by the LINKS phase: parents attach through `TasksService.attachImportedChild` (same rules as a normal move: project, cycle, depth including the child's subtree, tree lock); dependencies are checked for BLOCKS loops against the database. Unresolvable links are reported (`PARENT_MISSING`, `DEPENDENCY_MISSING`), never silently dropped.
7. **Workflow statuses are referenced per project** (`statusRefId`): Jira shares one status id across many projects while each project has its own workflow. (Found by a test: keyed by id alone, a second project's tasks pointed at the first project's statuses.) A workflow missing To Do / In Progress / Done is completed with synthetic statuses by the mapping (ADR-0006 requires all three); over 30, the overflow folds into its category's first status.
8. **Rows that were matched, not created, never belong to the import**: an issue type with the same name gets a `:reused` ref. Tags are matched by name (created ones get a ref). Custom fields are always created per the mapping.
9. **Silent history, one summary.** Writes use `{origin: IMPORT, silent: true, importJobId, keepOriginalDates}` (ADR-0003): no activity of an import reaches the feed; one `IMPORT_COMPLETED` audit row per job. Original `createdAt` / `updatedAt` are kept when the option is on.
10. **Metering.** Before each page, `checkLimit('importItems')` for the page's tasks (conservative: includes ones that will be skipped); the charge happens per chunk inside the chunk's transaction and is recorded in `progress.chargedByPeriod`, so a rollback refunds exactly what was charged, in the month it was charged. Projects are checked against the plan's project cap inside the project transaction.
11. **Findings about a person or value are reported once per JOB** (`USER_UNMAPPED`, `PRIORITY_UNMATCHED`, ...), checked against the stored issues, so they also hold across resumes (the mapping reports once per page).
12. **Progress** is pushed over the existing per-user SSE channel (`sse:user:<id>`, Redis pub/sub, type `IMPORT_PROGRESS`); best effort, never fails an import. The job row stays the truth.
13. **Rollback never deletes anything a person added afterwards.** It walks `ExternalRef` by `importJobId`: tasks leaf-first (a task that gained a subtask is KEPT), then projects (kept if they hold other tasks), custom fields (kept if values remain), issue types / iterations (kept if still used), tags (kept if still attached); `ROLLBACK_KEPT` (INFO) says what and why; every handled reference is released, so nothing dangles. Refunds the meter and finishes in ONE transaction (a retry never refunds twice). Idempotent and resumable; a second request is refused by the state machine. `DomainEraser` is the delete side of the single door (tasks, projects, custom fields). Activity rows of deleted tasks go with them.

## Not in 4.4 (by design)
Comments, history, attachments (4.6: they join `afterChunk` and the `ROLLBACK` order); **updating** a task whose source content changed since an earlier import (a re-run SKIPS existing tasks and records the hash; reported as `skipped`); project dates / archived flag; option merging for an EXISTING select field (a value that is not one of its options is left out, with an INFO); per-project target selection. Nothing registers `imports.run` unless `FEATURE_IMPORTS` is on (queue flag).

## Consequences
Domain files changed (additive): `DomainWriter` (`afterChunk`, `createProject(..., extras)`, `attachImportedChild`, `DomainEraser` export), `ProjectsService.create(..., extras)`, `TasksService.attachImportedChild`, `CustomFieldsService.validateValue` made public, `channelFor` exported from the SSE registry, `ImportsWorkerModule` added to the worker app.
