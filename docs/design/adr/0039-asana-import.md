# ADR-0039 - Asana connector and importer (step 4.10)

Status: Proposed by the builder; every decision names its alternative. Same shape as ADR-0036 (ClickUp), which this follows closely.

## How the research was done (and what it is worth)
No Asana workspace, OAuth app or API response was available. Shapes come from Asana's public documentation (developers.asana.com: OAuth, OAuth scopes, pagination, rate limits, attachments, the object reference) and third-party typed clients. **Every shape below is therefore unverified against a live response.** The fixtures are synthetic. First live run: record real responses and extend a contract spec (like Linear's).

Facts taken from the documentation and relied on:
- OAuth 2: authorize `https://app.asana.com/-/oauth_authorize`, token `.../-/oauth_token`, revoke `.../-/oauth_revoke`. PKCE (S256) is supported. **Access tokens last one hour; a refresh token is issued** (`grant_type=refresh_token`; the answer carries no new refresh token, so the stored one stays). Revocation takes the refresh token. The token answer includes the person (`data.gid / name / email`).
- **Scopes are granular** (`projects:read`, `tasks:read`, ...). An app registered with "Full permissions" must use `default` instead; a scoped request from such an app is refused.
- Pagination: `limit` 1-100, then `next_page.offset`; **offset tokens expire**.
- Rate limits: 150 requests/minute per token on a Free domain, 1,500 on a paid one, a cap on concurrent requests, and a separate **cost limiter** (a request is rated by how much of the object graph it walks), so `opt_fields` is kept narrow. A 429 carries `Retry-After`.
- Attachments: `GET /attachments?parent=<task>` lists them; each has a `host` (`asana`, `gdrive`, `dropbox`, ...) and, on its own `GET`, a `download_url` that is short-lived.

### Where this corrects the handoff
1. **Scope gap.** The documented scope table lists `tasks:read` for `/sections/{gid}/tasks` but not for `GET /projects/{gid}/sections`. With granular scopes that call may answer 403. Handled (decision 2).
2. **A cost limiter exists** on top of the per-minute limit (above).
3. **Offsets expire**, which weakens the "re-fetch the same page" contract (decision 8).
4. `download_url` is documented both as an `app.asana.com` address that redirects and as a direct signed storage address (decision 9).
5. ClickUp's `MAX_LISTS = 500` is above the bundle page limit of 200 projects (see "Found while building").

## Decisions
1. **A connection is the person's Asana account, not one workspace.** The token covers every workspace the person is in and the consent screen has no workspace picker, so ClickUp's "refuse when ambiguous" would lock out anyone in two workspaces. `externalAccountId` = the user gid. The source tree is workspace (not selectable) -> team (selectable; the Space analogue) -> project (selectable); a team is derived from its projects' `team`, so no teams call is needed; team-less projects hang from the workspace. *Alternative:* one connection per workspace, refusing more than one (rejected: wrong for the common case). `workspaceNodeType` is left unset (per-team workspaces are possible later, backlog #19).
2. **Sections are statuses (diagram 07).** Each section -> a status with category `UNKNOWN` **on purpose**, so the existing suggestion engine judges the name and the person sees it as a guess (tested through `suggestStatus`: "Done" MEDIUM, "In progress" MEDIUM, "Waiting on client" -> Blocked LOW, "Backlog" TODO LOW). A synthetic **Completed** (DONE) holds every task with `completed = true` whatever its section; a project with **no sections** gets a synthetic **To do**. Ids are `<project>:<section>`. If sections cannot be read (the scope gap) the import still runs: tasks are To do / Completed and the section name becomes a **tag**; the preview says so (`SECTIONS_UNAVAILABLE`). *Alternative:* section -> tag only, one status (rejected: loses the board). *Consequence:* a completed task forgets which column it was in.
3. **A task in several selected projects is imported into each of them** (owner's decision), as separate tasks with id `<project>:<task>`. Each copy gets its own section status, its own subtasks, comments and files (so the content requests repeat per copy; the preview warns `MULTI_PROJECT_DUPLICATED`). Tasks are read per project (`/projects/{gid}/tasks`), so no membership logic is needed. *Alternative:* first project only (rejected by the owner). *Limit:* the writer sees the copies as unrelated tasks; they are not linked.
4. **Subtasks** are read with `GET /tasks/{gid}/subtasks` through a **queue held in the cursor**, drained before the next task page, so a page can never exceed 1,000 tasks (parents are read 100 at a time; subtasks of queued parents are added while the page holds fewer than 500). A subtask inherits its parent's section status while open (it has no section) and is Completed when done. Cap: 500 subtasks per parent.
5. **Dependencies.** `task.dependencies` are the task's *blockers*, so the edge is blocker -> this task (`BLOCKS`), one id per edge (`dep:<project>:<blocker>><task>`). The other end is assumed to be in the **same project copy**; an edge whose other end is not part of the import stays pending in the writer and is dropped. Cross-project dependencies are therefore lost (backlog #20). *Unverified:* whether `dependencies` can be requested through `opt_fields` on the list endpoint.
6. **Priority is a mapped field, not a table.** Asana has no priority; teams use an enum custom field. The suggestion is the enum field named exactly "Priority" (its enabled options feed the mapping inventory; the field is *not* also a custom field). The generic table already reads High / Urgent / P0..P4. The per-source picker the owner chose (heuristic as suggestion) is the shared extension of ADR-0040, built right after this one; **Asana does not use it yet** (it would cost one `custom_field_settings` call per project in `discover`), so the heuristic is the only mechanism for now (backlog #21).
7. **Custom fields** are Workspace-wide in our model (identified by gid). Mapped: text, number, enum, multi-enum, date, people (first person). Not mapped, reported by kind and count: formula, reference and anything else. Per-page caps follow `CANONICAL_LIMITS` (a page over a limit is fatal, not truncated): 200 projects, 2,000 users, 500 fields, 2,000 tags, 5,000 dependencies; fields beyond the cap are dropped with `CUSTOM_FIELDS_CAPPED`.
8. **Cursor and expiring offsets.** `{ projects[], first[], fb, i, off, subs[] }`, plain JSON. `off` is the offset *used* to fetch the current page, so re-sending a cursor re-fetches the same page. Because offsets expire, a re-fetch long after the first read can fail; the executor's retry then hits a 400. *Unverified* (how long an offset lives, and what the error looks like); *Alternative:* store a skip count and restart the project from page 1 on failure (not built; wait for real behaviour).
9. **Files.** A `CanonicalAttachment.providerRef` is the opaque `asana-attachment:<gid>` (digits only), **never an address**. `fetchAttachment` asks `GET /attachments/{gid}` for a fresh `download_url` at copy time (they are short-lived), refuses anything that is not Asana-hosted (`host = asana`), and checks the address: `https`, no port, no userinfo, host `asana.com` / `*.asana.com` (the token is sent) or an `asana*` S3 bucket (signed URL, **the token is never sent**: S3 rejects two credentials). Anything else is refused before a request (mutation-checked). Files on Drive / Dropbox / Box are links, not copies, and are skipped.
10. **History is NOT imported.** Asana's system stories are prose ("X marked this complete"), not field changes; parsing English would invent data. The preview says so (`HISTORY_NOT_AVAILABLE`). *Alternative:* parse the common system stories into status / assignee changes once real responses are available (backlog #22).
11. **Pacing.** Per-request bucket, default 120/minute (`ASANA_REQUESTS_PER_MINUTE`, 10-10,000; a paid domain allows 1,500). Comments and files cost one request per task each (per copy); the preview computes the time (`CONTENT_SLOW`).
12. **Comments** are stories of subtype `comment_added` only (system events excluded), `html_text` -> markdown with the existing normaliser, oldest first. Task descriptions: `html_notes` -> markdown, `notes` as the fallback. Milestones and approvals -> issue types.

## Found while building (by the tests)
- With sections unreadable, tasks still pointed at a status taken from their memberships (e.g. `p1:s2`) that did not exist on the structure page: **dangling statuses**. Fixed in `openStatusOf`; the test asserts every task's status exists on the structure page.
- A page's collections are limits, not hints: the structure page would have been **fatal** above 500 fields. Caps now come from `CANONICAL_LIMITS`.
- **Not in Asana's code, but found on the way:** ClickUp's `MAX_LISTS = 500` is above the 200-projects-per-page limit, so selecting 201-500 lists fails the structure page with `PAGE_TOO_LARGE`. One-line fix (`MAX_LISTS = CANONICAL_LIMITS.maxProjects`); not changed here.

## Unverified (list for the first live run)
`GET /projects/{gid}/tasks` includes completed tasks and **excludes subtasks**; whether `memberships.section`, `dependencies`, `custom_fields.*` can all be requested through `opt_fields` on the list endpoint and what that costs under the cost limiter; whether `GET /projects/{gid}/sections` and `/custom_field_settings` answer 403 under granular scopes and which scopes cover them; `task_counts` (does `num_tasks` include subtasks?); the token endpoint's refresh answer (no `refresh_token`, `expires_in`); revoke with the refresh token; `data.gid` in the token answer; offset lifetime and error; attachment `host` vs `resource_subtype`, whether the token is needed for an `app.asana.com` `download_url`, the real storage host names; `stories` fields (`resource_subtype = comment_added`, `html_text`); `/workspaces/{gid}/users` visibility for guests; `team` on the project in the workspace listing; whether `archived=false` is the default on team projects.
