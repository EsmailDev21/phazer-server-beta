# How this baseline migration was produced

Normally `prisma migrate dev --name baseline` generates this file using Prisma's
**schema-engine**, a binary downloaded from `binaries.prisma.sh` on first use.
The environment this migration was authored in has no route to that host (and
no Docker, so no way to run the engine another way), so the schema-engine could
not be used — `prisma validate` and `prisma generate --no-engine` work (they
use a bundled WASM schema parser), but `migrate dev`, `migrate diff`, `db push`
and `db pull` all require the real engine and do not.

So `migration.sql` was **hand-generated by a small script** (`gen_ddl.py`,
kept alongside this note — see below) that parses `schema.prisma` and emits
`CREATE TYPE` / `CREATE TABLE` / `ALTER TABLE ... FOREIGN KEY` / `CREATE INDEX`
statements, in the same order Prisma itself uses (enums → tables → indexes →
foreign keys → implicit many-to-many join tables).

## Why you can trust it (verification, not just generation)

A hand-written generator is exactly the kind of thing that has subtle bugs, so
this wasn't taken on faith. Postgres 16 and Redis were available in the build
sandbox (via `apt`, even without Docker), so the migration was actually
**applied to a real database and checked, three independent ways**:

1. **The SQL applies cleanly, once, in one transaction** — `psql -f
   migration.sql -v ON_ERROR_STOP=1` against an empty database.
2. **Structural cross-check** (`crosscheck.js`) — independently re-parses
   `schema.prisma` and queries `information_schema.columns` /
   `information_schema.table_constraints` on the live database, comparing
   every table, column, nullability, type and foreign key against what the
   schema declares. **Result: 37/37 tables, 315/315 columns, 50/50 foreign
   keys matched, 0 problems.**
3. **Enum check** (`enumcheck.js`) — compares every `pg_enum` value, in order,
   against every `enum` block in `schema.prisma`. **Result: 35/35 enums
   matched exactly, 0 problems.**
4. **Functional smoke test** (`smoke.js`) — real `INSERT`/`DELETE` statements
   proving behavior, not just shape: column defaults actually fire
   (`status` → `TODO`, `createdVia` → `SNAP`, `isArchived` → `false`), the
   `_TaskAssignees` many-to-many join table round-trips, the `Comment`
   self-relation (`parentCommentId`) accepts a real parent row, `onDelete:
   SetNull` on `Task.projectId` actually nulls the column instead of blocking
   the delete, a relation *without* an explicit `onDelete` (`Task.createdBy`)
   correctly defaults to `RESTRICT` and rejects the delete, and the
   `@@unique([workspaceId, key])` constraint on `CustomField` rejects a real
   duplicate insert. **10/10 assertions passed.**

This loop caught two real bugs before they reached this file, both from the
same root cause — a regex (`@default\(([^)]*)\)`) that stops at the *first*
`)`, so it mis-captured `@default(now())` as `now(` instead of `now()`:

- Every `createdAt` / `updatedAt` column silently lost its `DEFAULT now()`.
- `Comment.replies` (a self-relation, one-to-many via `parentCommentId`) was
  briefly misdetected as an implicit many-to-many, because the m2m detector
  didn't exclude a field from matching against itself on a self-relation.

Both are fixed in `gen_ddl.py`; the numbers above are from the run *after*
the fixes, not before.

## What this does **not** prove

- That Prisma's own schema-engine would generate **byte-for-byte identical**
  SQL. It should be semantically equivalent (that's what the checks above
  establish), but formatting, statement order, or constraint naming may
  differ from what `prisma migrate dev` would have produced natively.
- Anything beyond what `information_schema` and the smoke test cover —
  e.g. `CHECK` constraints (this schema has none) or exotic index types
  (this schema only uses default B-tree; the two `@@unique`/`@@index`
  compound cases were included in the cross-check's index count but not
  individually asserted by name).

## What to do about that

Once you have a normal network connection, run:

```bash
npm run db:verify
```

This calls `prisma migrate diff --from-migrations prisma/migrations
--to-schema-datamodel prisma/schema.prisma --exit-code`, i.e. it asks
Prisma's **real** schema-engine whether this migration reproduces
`schema.prisma` exactly. It costs nothing to run and is the authoritative
check — treat this baseline as provisional until that command passes on your
machine, and if it ever reports drift, trust `db:verify`, not this note.

## Files kept for reference

The scripts used to generate and verify this migration are committed in
`tools/` (`gen_ddl.py`, `crosscheck.js`, `enumcheck.js`, `smoke.js`) — not
part of the app, but kept so the method is fully auditable and reusable. See
`tools/README.md` to re-run them.

## A real gap this verification loop had, found and fixed in step 0.6

`crosscheck.js` confirms every table/column **exists** with the right shape;
`enumcheck.js` confirms every enum's **values** match. Neither one checks
whether `schema.prisma` itself correctly **declares** the names this
migration actually created — and it didn't, for any of them. This migration
creates snake_case columns (`google_id`) and snake_case enum types
(`creation_mode`), matching every table's own `@@map("...")`, but
`schema.prisma` had **zero** `@map`/`@@map` on any individual field or enum
(only on models). Prisma's default with no `@map` is to use the
Prisma-schema name **verbatim** as the database identifier — so
`schema.prisma`, as written, told Prisma Client the column was called
`"googleId"`, a column that has never existed. Every multi-word field
(208 of them, all 37 models) and every enum type (all 35) had this same gap.

`enumcheck.js` didn't catch its own half of this because it computes the
expected Postgres type name **itself**, with the identical snake-casing
regex the generator uses (`pgname = snake(name)`), rather than reading
`schema.prisma`'s (nonexistent) `@@map` — so it was really only checking
"does the generator agree with itself twice," not "does `schema.prisma`,
read the way Prisma actually reads it, agree with the database." `smoke.js`
didn't catch it either, because it uses the raw `pg` driver directly with
hand-written snake_case SQL, never Prisma Client — so no tool in this
directory ever actually asked Prisma to generate SQL from `schema.prisma`
against this database. Fixed by adding the missing `@map`/`@@map` to
`schema.prisma` itself (a schema-only change — this migration's SQL needed
no edit, since the database was already correct; only `schema.prisma`'s
declared understanding of it was wrong). `scripts/verify-schema-mapping.js`
(new in step 0.6, offline, no DB or engine needed) checks this specific
property going forward — see PROGRESS.md for the full account.
